### Anthropic Donates Agent Skills to the Agentic AI Foundation, Handing the Standard to a Neutral Foundation

- What happened: On 10-22 Anthropic announced it is donating the Agent Skills open standard to the Agentic AI Foundation (AAIF) under the Linux Foundation, along with the name, the logo, the GitHub organization and the agentskills.io domain. Maintainers serve in a personal capacity and come from Anthropic, Google, OpenAI and other companies; the Lead Maintainers are David Soria Parra and Mahesh Murag; the stated roadmap has three items: versioned releases, a formal proposal process, and security guidance for the people who write and install skills. The company says more than 70 agent platforms have already integrated it, including ChatGPT, Cursor, GitHub Copilot and VS Code, with 1 million skills published and nearly 280 million installs. This is not the first time: MCP was donated to the same foundation last year in exactly the same way.
- Why it matters: Skills are the cheapest interoperability layer right now — one folder plus one SKILL.md lets any agent learn a task — so whoever holds the right to evolve this format shapes the capability boundaries of a whole set of products. Handing it to a neutral foundation means spec changes must go through public proposals rather than follow a single vendor's release cadence; conversely, Anthropic turns itself from "owner of the standard" into "one of the primary maintainers", precisely the MCP path. The real variable is the security guidance item: skills can carry scripts and can require installs, and there is currently no unified agreement on the distribution security of third-party skills.
- Original posts and engagement: [FirstSquawk's news alert](https://x.com/FirstSquawk/status/2113335401213739137) (10-23 02:23, 19K views, 6 likes, 0 reposts, 2 replies) compresses the donation and the roadmap into a single wire-style item; [Techmeme's entry](https://x.com/Techmeme/status/2113370134614335842) (10-23 04:41, 2,547 views, 8 likes, 0 reposts, 3 replies) adds the background of "following the 2025 MCP donation"; [a participant's personal post @dsp_](https://x.com/dsp_/status/2113334259952066587) (10-23 02:18, 1,358 views, 21 likes, 3 reposts, 3 replies) names Earendil (PI), OpenCode, Microsoft, Google and OpenAI as co-advancing the standard — names the official blog did not list; the technical breakdown from [@rohanpaul_ai](https://x.com/rohanpaul_ai/status/2113363238390046931) (10-23 04:13, 2,604 views, 21 likes, 4 reposts, 14 replies) explains the structure of a skill and where "1M skills / 280M installs" comes from. Engagement on all four posts is low, indicating this is a developer-side announcement rather than a consumer hot topic.
- Verification: [Anthropic's official blog](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation) confirms the scope of the donation (standard, name, logo, GitHub organization, agentskills.io domain), the AAIF affiliation and the "co-founded with Block and OpenAI" wording, the two Lead Maintainer names, the 70+ platforms and the 1M skills / 280M installs figures, and the three roadmap items; [agentskills.io](https://agentskills.io/home) and the [agentskills GitHub organization](https://github.com/agentskills/agentskills) are already given in the text as entry points for the spec and for discussion; [Simon Willison's write-up](https://simonwillison.net/2026/Oct/22/donating-agent-skills/) independently restates the same set of facts. The blog's timeline is that skills shipped with Claude Code in October 2025 and were released as an open standard that December; the 70+ / 1M / 280M figures are all company self-reports with no third-party statistics.
- Assessment: The weight of this item is not "yet another foundation" but that the governance cost of the standard has been priced in advance: once the proposal process and security guidance land, judging skill compatibility shifts from "reading Anthropic's docs" to "reading the version number". The direct implication for downstream teams is that skills written now need to start considering version pinning; for Anthropic this is the second time it trades "build a de facto standard first, then hand it over" for ecosystem defaults, at the price of losing the freedom to change the spec unilaterally.

### Recursive Open-Sources Flint: a 40B MoE Local Coding Model, and the 89.7% on SWE-bench Pro v2 Is Vendor-Reported

- What happened: On 10-21 Recursive Superintelligence released its first model, Recursive Flint, with Apache 2.0 open weights, 39.8B total parameters, roughly 2.5B active (6 of 256 routed experts plus 1 shared expert), 49 layers, aimed at local coding agents. The company self-reports SWE-bench Verified 74.2%, SWE-bench Pro v2 89.7% and Terminal-Bench 2.1 54.9%; paired with its own inference engine rec, it runs at 125+ tokens/s on an M4 Pro MacBook Pro and 150+ tokens/s on a 64GB RTX Spark, roughly twice comparable models at short context. The model was built with participation from the company's own automated research system Eureka Machine, and the company says it went from zero to launch in under four months. It was available free on OpenRouter at launch and supports llama.cpp, Ollama, LM Studio, vLLM and SGLang.
- Why it matters: Coding models that simultaneously satisfy all three conditions — 40B class, 2.5B active, fits on a laptop — have been rare, and this turns "data never leaves the machine" from compliance talk into an executable plan. More interesting is the production method: the blog attributes architecture search, the 4-bit quantization recipe (even the output layer is quantized to 4 bit, with accuracy recovered via offline distillation) and the Metal megakernel to Eureka Machine, while the NVIDIA side says these purpose-built kernels raise generation speed on RTX Spark by 55% without changing the weights. If this narrative holds, it means "model capability" and "model construction pipeline" have been split into two reusable assets.
- Original posts and engagement: [OpenRouter's official listing post](https://x.com/OpenRouter/status/2113007405563052313) (10-22 04:39, 18K views, 227 likes, 19 reposts, 15 replies) lists the three results one by one and labels them "Recursive reports"; [the most widely spread English post @slash1sol](https://x.com/slash1sol/status/2112971830826848662) (10-22 02:18, 4,322 views, 88 likes, 5 reposts, 29 replies) stresses "no API bill, code stays on the laptop"; [MarktechPost's technical breakdown](https://x.com/Marktechpost/status/2113039632053260304) (10-22 06:48, 1,272 views, 15 likes, 11 reposts, 5 replies) gives the sparsity and the post-quantization memory footprint and points out the cost: on Terminal-Bench 2.1 Flint scores 54.9%, below dense Qwen 3.8's 73.0%.
- Verification: [Recursive's official blog](https://recursive.com/updates/introducing-recursive-flint) and the [Hugging Face model card](https://huggingface.co/RecursiveSI/flint) confirm the parameter structure, Apache 2.0, the four speed figures and the three benchmarks, as well as the evaluation setup (Terminus 2 for Terminal-Bench, mini-swe-agent for SWE-bench, no network access, at least 5 runs averaged). On the 89.7% figure, one thing needs to be clear: it was not invented by Chinese posts — the model card itself reads "89.7% on SWE-bench Pro v2", and OpenRouter copied it and noted it is vendor-reported; the problem is that there is no third-party reproduction. Moreover, SWE-bench Pro is usually harder than Verified, so an inversion where "Pro v2 89.7 is higher than Verified 74.2" means the harness, attempt counts and grading methods behind the two scores must be compared item by item before they can be accepted; this article records it only as a vendor-reported value. Context length also differs by source: the blog says "supported up to 512k, recommended to stay within 256k", the model card says "documented context configuration 262,144", and OpenRouter says 262K, so the model card's 262K is taken as authoritative. See also [TechCrunch's report](https://techcrunch.com/2026/10/21/recursive-launches-flint-a-laptop-coding-model-it-says-was-largely-built-by-ai/) and the 55% speedup claim in [NVIDIA's local AI blog](https://blogs.nvidia.com/blog/local-ai-gtc-rtx-dgx-spark-station-sync/).
- Assessment: This is the most worth-reading item of the issue and also the one that most needs restraint. The hard, verifiable facts are the license, the parameter count, the roughly 23GB footprint after quantization, the ability to run on a single machine, and the "under four months" timescale; what cannot be verified are the benchmark scores and the claim that "Eureka Machine was involved in building almost every layer". The thing actually worth interrogating is the two inverted numbers, not the big number that spread the widest.

### OpenAI Decisions API Generally Available: Billed on Input Only, Up to 400 Questions per Request

- What happened: On 10-22 OpenAI moved the Decisions API from beta to general availability. Calls go to a separate /v1/decisions endpoint and currently support only GPT-6 Luna; a single request submits shared input (text, images, structured JSON, conversation history including tool calls) together with 1 to 400 questions, returning three types of bounded answers: predicate gives a probability from 0 to 1, choice picks one of preset options with per-option probabilities, and score gives a weighted average on a 2-to-10 rating scale. The company says it is up to 10x faster than calling Luna through the Responses API; since the beta it added native GPT-Live integration, prompt caching, inference residency in the US and Europe, and raised the per-request question limit from 200 to 400.
- Why it matters: This is a pricing experiment that peels "judgment" out of generation. The price is $0.10 per million input tokens and $0.01 per million cached input tokens, with output not billed; for high-frequency, low-complexity calls such as classification, routing and blocking, the cost structure is an order of magnitude lower than "have the model write a paragraph and then parse it". The customer data the company cites clusters in this direction too: Sierra says choosing the next action in live conversations has a p95 under 280 milliseconds with 90% lower cost per call; Datadog says it scores risk before executing shell commands generated by agents, with p95 latency 40x faster than frontier models.
- Original posts and engagement: [OpenAI's developer account post](https://x.com/OpenAIDevs/status/2113346642787086538) (10-23 03:07, 63K views, 858 likes, 56 reposts, 104 replies) is the only first-hand source for this item on X and one of the highest-engagement model-side posts of this issue.
- Verification: The body of [OpenAI's official announcement page](https://openai.com/index/decisions-api/) returned 403 and could not be read directly, so this was cross-checked against [the Decisions guide in the developer docs](https://developers.openai.com/api/docs/guides/decisions) and [Unite.AI's item-by-item writeup](https://www.unite.ai/openai-makes-decisions-api-generally-available-with-gpt-6-luna/): confirming the endpoint, the three question types, Luna as the only supported model, the 400-question cap, the "up to 10x faster" wording, and the pricing of $0.10 per million input tokens with $0.01 for cached input and input-only billing. The source material's claim that "output is free" holds, but note the official wording is "no charge for output tokens", while regional processing premiums and long-context multipliers are still billed separately, and cache read/write rates match Luna's standard prompt caching. The docs also state that files, audio and item references are not supported, and that decisions depending on a previous answer must be split into multiple requests.
- Assessment: What is worth remembering is not the 10x but the change in billing basis: cutting cost down to input only amounts to encouraging "many questions in one call", which directly changes an agent's call structure — from "ask the model once per step" to "ask 400 judgments at once". The risk sits in the same place: 400 questions share a single context, and the more correlated the questions are, the more likely they are to be wrong together.

### Google Launches Agent Compute Engine at AGNTCon and Extends Gemini's Enterprise Agent Governance

- What happened: On 10-22 at AGNTCon + MCPCon, Google Cloud announced Agent Compute Engine (ACE), a compute service purpose-built for the agent lifecycle that currently powers Gemini's worker agents and will enter preview in the coming months. Each agent gets a hardware-isolated microVM: a Cloud Hypervisor boundary, an independent guest kernel with root, its own Hyperdisk for session persistence, short-lived credentials and a cryptographically verifiable ID, with credentials injected at an egress point outside the microVM; idle microVMs are paused via checkpoint/restore to save resources, and multiple agents share a single system template through copy-on-write. In the same period it expanded Gemini for business agent governance into components such as Agent Gateway and Agent Registry, and open-sourced Agent Substrate, a runtime that runs on GKE.
- Why it matters: In the cost structure of multi-agent systems, what is really expensive is waiting: an agent holds a machine while it waits for a tool to return or a human to confirm. ACE's design and Agent Substrate's measured figures point at the same thing: driving idle-state cost close to zero. Google's numbers are that Agent Substrate sustained 500 activations per second in a stress test with 200,000 agents, with suspend and resume latency under 500 milliseconds and compute density up to 10x that of conventional approaches. For buyers, this means the seemingly expensive model of "one machine per agent" finally has a workable price.
- Original posts and engagement: [Google Cloud's official post](https://x.com/googlecloud/status/2113285915258794378) (10-22 23:06, 21K views, 197 likes, 27 reposts, 18 replies). The Gemini API CLI the same day was announced first by two Google employees: [EvanOtero](https://x.com/EvanOtero/status/2113342374713938089) (10-23 02:51, 6,144 views, 99 likes, 4 reposts, 5 replies) and [vamsibatchuk](https://x.com/vamsibatchuk/status/2113309268216778905) (10-23 00:39, 3,871 views, 101 likes, 4 reposts, 10 replies); the official account did not post about it separately.
- Verification: [Google Cloud's official blog](https://cloud.google.com/blog/topics/ai-infrastructure/introducing-agent-compute-engine-and-expanded-agent-governance) confirms the microVM architecture, silicon-level isolation via Titanium IPU, Hyperdisk persistence, the governance scope of Agent Gateway and Agent Registry, and the "coming months" preview timing (some media wrote "later this year", slightly different from the official text). [The GKE Agent Substrate blog](https://cloud.google.com/blog/products/containers-kubernetes/agent-substrate-available-on-gke) confirms the 10x density, 500 activations per second, the 200,000-agent stress test and open-source portability. The Gemini API CLI (gemini-api) is confirmed by [the official repository](https://github.com/google-gemini/gemini-api-cli): a single Apache 2.0 Go binary in preview/experimental status covering text generation, images (gemini-nano-banana-2.1 by default), TTS, music (lyria-3.5), video (gemini-omni-1.1-flash), file analysis and transcription, able to write media files straight to disk and return only the path, with --dry-run and --schema for agents to self-check, and hosted agents can run in the background and return an interaction ID.
- Assessment: ACE and the CLI are two ends of the same thing: one standardizes an agent's runtime into "one virtual machine per agent", the other packages Google's model capabilities into a command line that agents can call directly. For third-party agent frameworks the latter is more realistic than the former — no cloud migration needed, just one more executable in the shell. The question to keep is the preview timing: the official line is "in the coming months", and the full chain of agent governance and enterprise identity usually comes online far more slowly than compute does.

### Hugging Face Open-Sources Carbon-X: a 14B Model That Reads DNA, 0.8 Points Behind the Frontier but About 1,800x Cheaper

- What happened: On 10-22 Hugging Face released Carbon-X, a 14.8B-parameter joint DNA and natural-language model built from Qwen3-14B under Apache 2.0. The approach is a single decoder with a single token stream: text keeps Qwen3's BPE vocabulary, while DNA is encoded into one token per non-overlapping 6-mer, for 5,515 DNA tokens in total, with no separate DNA encoder; mid-training used 302B tokens of DNA, biology text, English and instruction data, followed by SFT and reinforcement learning with verifiable rewards. It averages 66.7% across five DNA benchmarks, which the company says is 27 points above the base Qwen3-14B and slightly below GPT-6.1 Sol's 67.5%, while inference cost per question is about 1/1800 of the latter; the bf16 weights fit on a single 80GB card. In the same period Clement Delangue and Thom Wolf publicly criticized frontier labs' biosecurity filters for shutting scientists out.
- Why it matters: Turning DNA into an ordinary vocabulary extension of "one token per 6 bases" lets the model read sequences directly in a conversation and explain the reasoning behind its judgment, which is closer to how researchers actually work than building a separate specialized model: paste a sequence, ask a question, get an answer with reasoning. The cost part is the real point: the company estimates that analyzing the 2.4 million variants of uncertain significance in ClinVar with Carbon-X would cost about $300, versus $32,000 to $4 million for the frontier models they evaluated.
- Original posts and engagement: [The author @_lewtun](https://x.com/_lewtun/status/2113214040516268126) (10-22 18:21, 19K views, 203 likes, 32 reposts, 27 replies) gives the claim of "close to GPT-6.1 Sol at over 1,000x lower cost"; [Clement Delangue](https://x.com/ClementDelangue/status/2113264393756545449) (10-22 21:41, 56K views, 905 likes, 115 reposts, 55 replies) criticized that "frontier labs are racing ahead on biological capability while blocking scientists with broad, shallow guardrails, and bad actors get around them easily", and said he himself was blocked by a link; [Thom Wolf](https://x.com/Thom_Wolf/status/2113345703485309335) (10-23 03:04, 7,484 views, 102 likes, 12 reposts, 18 replies) told a concrete joke: while writing that post the assistant was cut off by a biosecurity filter, and what it was summarizing was his own company's model notes released that day.
- Verification: [The model card](https://huggingface.co/HuggingFaceBio/Carbon-X) confirms 14.8B parameters, the Qwen3-14B base, 6-mer tokenization, 302B mid-training tokens, a 40,960-token context, Apache 2.0, the 66.7% versus 67.5% comparison and the original "about 1/1800 cost per question" wording — note the company writes 1/1800, while the source material's "over 1,000x lower" is a conservative paraphrase; the two point the same way but with different precision. The same page also states that Carbon-X is not clinically validated, must not be used for medical decisions, and lists limitations such as long inputs not being fully evaluated and thinking mode not being trained. [Hugging Face's release page](https://huggingface.co/spaces/HuggingFaceBio/Carbon-X-Release) and [Business Insider's report](https://www.businessinsider.com/hugging-face-ai-model-carbon-x-dna-sequences-gene-therapies-2026-10) add the partners (Zhongguancun Academy, TIGEM/University of Naples Federico II) and the "conversational DNA reading" positioning. [The Next Web](https://thenextweb.com/news/hugging-face-carbon-x-dna-ai-model) also notes the model has no wet-lab validation yet.
- Assessment: The 0.8-point gap does not deserve to be treated as "catching the frontier"; what is worth recording is the cost curve: when per-question cost differs by three orders of magnitude, much of the large-scale variant screening that was previously impossible on budget becomes practical. The criticism from Delangue and Wolf is a statement of position, not a verifiable fact, but it points at a specific product problem: biosecurity filtering is currently neither transparent nor consistent, and the same assistant will block its own company's release notes — that kind of collateral damage is exactly why users leave.

### LiteLLM 1.107.0 Hit by Another Supply Chain Attack: Official PyPI Package and Docker Images Backdoored

- What happened: LiteLLM 1.107.0, released on 10-21, was found to be a malicious version, with all seven wheels on PyPI and the official Docker images (including the latest and main-stable floating tags) affected. The malicious code runs automatically at Python startup via the .pth mechanism and sitecustomize.py, stealing cloud credentials, AI provider API keys and SSH private keys, and fetching a domain from an attacker-controlled GitHub repository before pulling and compiling remote code for execution, enabling remote code execution; it also daemonizes via fork/setsid and maintains persistence with a /tmp lock file and roughly hourly polling. LiteLLM says the attacker operated through the GitHub accounts of three engineers, believes a GitHub CLI OAuth token was stolen, and that the attacker tried to modify the release pipeline so releases pointed at a different source repository. The safe version rolls back to 1.106.2, and the official source tag itself is clean — the problem was in the build environment. In the same week Railway, Zeabur and OpenCode each had security incidents too.
- Why it matters: LiteLLM is the unified entry point through which many teams connect to multiple model providers, and the environment it lives in naturally holds the keys to every provider, so one compromise equals exposure of all credentials. The technical details here are more worth copying into a checklist than "yet another poisoned package": the malicious files are not in the git tag but exist only in the build artifacts, so a process that reviews only source and diffs only tags cannot see it at all; and the startup hook means that "running pip uninstall inside the affected environment" itself re-triggers it.
- Original posts and engagement: [The Hacker News](https://x.com/TheHackersNews/status/2112967698103894257) (10-22 02:02, 64K views, 387 likes, 96 reposts, 38 replies) was among the first to spread it; [SlowMist](https://x.com/SlowMist_Team/status/2113113355917619560) (10-22 11:40, 3,447 views, 28 likes, 9 reposts, 15 replies) gave remediation advice and the specific version to pin at, 1.106.2; [DailyDarkWeb](https://x.com/DailyDarkWeb/status/2112971516690432179) (10-22 02:17, 5,944 views, 12 likes, 1 repost, 3 replies) added "92M+ monthly downloads" and the warning not to try to save yourself with pip; [a list post tying October together @infinterenders](https://x.com/infinterenders/status/2113148214115492337) (10-22 13:59, 4,625 views, 123 likes, 11 reposts, 10 replies) puts LiteLLM alongside Railway, Zeabur, OpenCode and others.
- Verification: [LiteLLM's official incident report](https://docs.litellm.ai/blog/security-incident-oct-21-2026) confirms "the GitHub accounts of three engineers, suspected theft of a GitHub CLI OAuth token", the attacker's attempt to point the publisher at another source repository, and the conclusion that the source tag contains no malicious files; [Upwind's analysis](https://www.upwind.io/feed/litellm-1-107-0-supply-chain-attack-malicious-code-found-in-pypi-package) (the party that found the vulnerability, credited in [GitHub issue #47826](https://github.com/BerriAI/litellm/issues/47826)) confirms that all seven wheels were affected, the cook.pth / cook.py / sitecustomize.py trio, that the delivery domain was a lookalike litellm.dev (unrelated to the official litellm.ai), and the hourly payload-fetching persistence; [Wiz's analysis](https://www.wiz.io/blog/litellm-compromised-steals-credentials) and [Help Net Security's report](https://www.helpnetsecurity.com/2026/10/22/litellm-compromised-supply-chain-attack-pypi-docker/) are consistent. Note that as of verification this incident was disclosed mainly through the official blog and third-party security vendors, and no corresponding entry had yet appeared in the GitHub advisory database.
- Assessment: Only three actions matter for users: confirm you never installed 1.107.0, rebuild from a clean image rather than uninstalling in place, and rotate every credential that environment could reach. The longer-term point is at the process level: a software bill of materials covering only source is not enough; the permissions of build artifacts and the release pipeline were the real entry point of this attack — three engineers' OAuth tokens were enough to change the release target, which shows that release permission is itself the highest-risk attack surface.

### MIT's OPAL Lets Agents Rewrite Optimizer Code During Training

- What happened: MIT researchers Xingjian Bai, Jia-Hao Liang, Jayden Teoh and Vincent Sitzmann released OPAL (OPtimizer with an Agent in the Loop) on 10-21: it puts an LLM agent inside the training loop to observe loss and gradient dynamics, read documentation, and then rewrite the source code of the optimizer itself rather than tuning hyperparameters from outside. Experiments cover four classes of image generation and language modeling tasks, and the authors say it beats or matches human recipes on LightningDiT-XL/1 (FID-50K 1.83 versus the official recipe's 2.18, with guidance), RAEv2-B (3.19 versus 3.39) and modded-nanogpt Track 3; each run makes about 100 decisions, costing about $6.42 in Claude Opus 5.5 tokens against roughly 74 H100-hours of training spend.
- Why it matters: This turns "optimizer design" from humans writing formulas into agents writing code, and it is explicitly zero-shot with no learning across runs. The cost comparison it gives is persuasive: token money is almost negligible next to GPU hours, which means "letting a model modify training code" is already economically a non-issue, and the problem shifts to reliability and auditability.
- Original posts and engagement: [Robert Lange's interpretation](https://x.com/RobertTLange/status/2113352327042117692) (10-23 03:30, 1,196 views, 37 likes, 2 reposts, 4 replies) stresses that "it is not an outer-loop hyperparameter tuner"; [Google's Laurence Moroney](https://x.com/lmoroney/status/2113143520831918485) (10-22 13:40, 734 views, 4 likes, 0 reposts, 4 replies) sums it up in one line as "the optimizer rewrites itself during training"; [a sharper comment @toankhontech](https://x.com/toankhontech/status/2113114737248809111) (10-22 11:46, 167 views, 4 likes, 0 reposts, 3 replies) points out that the repository itself admits most experiments were run only once and that the agent cannot roll back a bad decision. Engagement on all three posts is low, so this spread within research circles.
- Verification: [The authors' blog "Reactive Optimizers"](https://xingjianbai.com/reactive-optimizers/) is the main first-hand source, confirming the author list, the Claude Opus 5.5-driven agent, the specific numbers and cost accounting for the four task groups, and explicitly stating that the method is "fully zero-shot and learns nothing from repeated runs", while acknowledging that in FLOPs terms this approach is unrealistic at frontier scale — its positioning is that "for most researchers, GPU hours cost more than tokens". [The GitHub repository](https://github.com/xingjian-bai/opal) and [the PyPI description](https://pypi.org/project/opal-optimizer/) add engineering constraints: Claude Code must be installed and logged in locally (costs billed to the user's account, no cap by default), CPU-only single-GPU and single-node DDP are supported, and the agent can only change the program at the next decision point without restarting or rolling back training; the docs also warn that "a bad decision will make a run worse". The source material is inaccurate in calling this an arXiv paper: what is public is a blog with full footnotes and installable code, and no arXiv number could be found.
- Assessment: The correct reading of this item is "the cost argument holds, the reliability argument does not". About 100 decisions per run, most experiments run only once, and no rollback on failure — taken together, these three mean the variance of the conclusions has not been quantified. What will decide whether this enters production training is not those FID numbers but whether anyone builds a guardrail for "what happens when the agent breaks something".
