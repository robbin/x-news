### Anthropic 把 Agent Skills 捐给 Agentic AI Foundation，标准交给中立基金会

- 发生了什么：Anthropic 10-22 宣布把 Agent Skills 开放标准捐给 Linux 基金会下的 Agentic AI Foundation（AAIF），同时交出名称、logo、GitHub 组织与 agentskills.io 域名。维护者以个人身份来自 Anthropic、Google、OpenAI 等公司，Lead Maintainers 为 David Soria Parra 与 Mahesh Murag；提出的路线图是三件事：版本化发布、正式提案流程、面向写与装 skill 的人的安全指引。官方称 70 多个 Agent 平台已集成，包括 ChatGPT、Cursor、GitHub Copilot、VS Code，累计发布 100 万个 skill、安装近 2.8 亿次。这不是第一次：MCP 去年也是这样捐给同一个基金会的。
- 为什么值得关注：Skill 是当下最便宜的互操作层，一个文件夹加一份 SKILL.md 就能让任何 Agent 学会一项任务，所以谁掌握这份格式的演进权，谁就影响一批产品的能力边界。交给中立基金会意味着规范变更要走公开提案，而不是跟随单一厂商的发版节奏；反过来，Anthropic 也把自己从“标准所有者”变成“主要维护者之一”，与 MCP 的路径完全一致。真正的变量在安全指引那一项：skill 可以带脚本、可以要求安装，第三方 skill 的分发安全目前没有统一约定。

### Recursive 开源 Flint：40B MoE 本地编码模型，89.7% 的 SWE-bench Pro v2 是厂商自报

- 发生了什么：Recursive Superintelligence 10-21 发布首个模型 Recursive Flint，Apache 2.0 开源权重，39.8B 总参数、约 2.5B 激活（256 个路由专家里选 6 个，外加 1 个共享专家），49 层，面向本地编码 Agent。官方自报 SWE-bench Verified 74.2%、SWE-bench Pro v2 89.7%、Terminal-Bench 2.1 54.9%；配自研推理引擎 rec，在 M4 Pro MacBook Pro 上 125+ tokens/s、64GB RTX Spark 上 150+ tokens/s，短上下文下约为同类模型的两倍。模型由自家的自动研究系统 Eureka Machine 参与搭建，官方称从零到发布不到四个月。首发即上 OpenRouter 免费使用，并支持 llama.cpp、Ollama、LM Studio、vLLM、SGLang。
- 为什么值得关注：40B 档、2.5B 激活、能塞进一台笔记本，这三个条件同时成立的编码模型此前不多，它把“数据不出本机”从合规话术变成可执行方案。更值得看的是生产方式：博客把架构搜索、4-bit 量化配方（连输出层都量化到 4 bit，再用离线蒸馏补回精度）、Metal megakernel 都归给 Eureka Machine，NVIDIA 一侧的说法是这些专用 kernel 让 RTX Spark 上的生成速度提升 55% 而未改动权重。这套叙事如果成立，意味着“模型能力”与“模型构建流程”被拆成了两个可复用的资产。
- 原帖与互动：[OpenRouter 官方上架帖](https://x.com/OpenRouter/status/2113007405563052313)（10-22 04:39，1.8 万浏览、227 赞、19 转、15 回复）逐条列出三项成绩并标注“Recursive reports”；[传播最广的英文帖 @slash1sol](https://x.com/slash1sol/status/2112971830826848662)（10-22 02:18，4322 浏览、88 赞、5 转、29 回复）强调“没有 API 账单、代码留在笔记本上”；[MarktechPost 的技术拆解](https://x.com/Marktechpost/status/2113039632053260304)（10-22 06:48，1272 浏览、15 赞、11 转、5 回复）给出了稀疏度与量化后的内存占用，并指出代价：Terminal-Bench 2.1 上 Flint 54.9%，低于稠密 Qwen 3.8 的 73.0%。
- 核验：[Recursive 官方博客](https://recursive.com/updates/introducing-recursive-flint)与 [Hugging Face 模型卡](https://huggingface.co/RecursiveSI/flint)确认了参数结构、Apache 2.0、四项速度与三项基准，以及评测口径（Terminal-Bench 用 Terminus 2、SWE-bench 用 mini-swe-agent、无联网、至少 5 次取平均）。关于 89.7% 这个数字需要说清楚：它不是中文帖编出来的，模型卡原文就写“89.7% on SWE-bench Pro v2”，OpenRouter 也照抄并注明是厂商自报，问题在于它没有任何第三方复现；而且 SWE-bench Pro 通常比 Verified 更难，出现“Pro v2 89.7 高于 Verified 74.2”这种倒挂，说明两个分数对应的 harness、尝试次数与判定方式必须逐项对照才能采信，本文只把它当作厂商自报值记录。上下文长度也存在口径差：博客写“支持到 512k、建议控制在 256k 以内”，模型卡写“documented context configuration 262,144”，OpenRouter 写 262K，以模型卡的 262K 为准。另可参考 [TechCrunch 报道](https://techcrunch.com/2026/10/21/recursive-launches-flint-a-laptop-coding-model-it-says-was-largely-built-by-ai/) 与 [NVIDIA 本地 AI 博客](https://blogs.nvidia.com/blog/local-ai-gtc-rtx-dgx-spark-station-sync/) 中的 55% 提速说法。
- 判断：这是本期最值得看、也最需要克制的一条。可验证的硬事实是许可证、参数量、量化后约 23GB 的体积、单机可跑，以及“不到四个月”这个时间尺度；不可验证的是基准分数与“Eureka Machine 参与搭建了几乎每一层”的自述。真正该追问的是倒挂的那两个数字，而不是传播最广的那个大数字。

### OpenAI Decisions API 正式可用：只按输入计费，一次请求最多 400 个问题

- 发生了什么：OpenAI 10-22 把 Decisions API 从公测转为正式可用。调用走独立的 /v1/decisions 端点，目前只支持 GPT-6 Luna，一次请求把共享输入（文本、图片、结构化 JSON、含工具调用的对话历史）与 1 到 400 个问题一起提交，返回三类型的有界答案：predicate 给 0 到 1 的概率，choice 从预设选项里选一个并附各选项概率，score 按 2 到 10 级评分表给出加权平均分。官方称比经 Responses API 调用 Luna 快至多 10 倍；公测之后补上了 GPT-Live 原生集成、提示缓存、美国与欧洲的推理驻留，并把单请求问题上限从 200 提到 400。
- 为什么值得关注：这是把“判断”从生成里剥出来的定价实验。价格是每百万输入 token 0.10 美元、缓存输入每百万 0.01 美元，输出不计费；对分类、路由、拦截这类高频低复杂度调用，成本结构比“让模型写一段话再解析”低一个数量级。官方给出的客户数据也集中在这个方向：Sierra 称在实时对话里做下一步动作选择 p95 低于 280 毫秒、每次调用成本降 90%；Datadog 称在执行 Agent 生成的 shell 命令前做风险打分，p95 延迟比前沿模型快 40 倍。
- 原帖与互动：[OpenAI 开发者账号帖](https://x.com/OpenAIDevs/status/2113346642787086538)（10-23 03:07，6.3 万浏览、858 赞、56 转、104 回复），是本条在 X 上的唯一一手来源，也是本期互动最高的模型侧帖子之一。
- 核验：[OpenAI 官方公告页](https://openai.com/index/decisions-api/) 正文抓取返回 403，未能直接读到，改以 [开发者文档的 Decisions 指南](https://developers.openai.com/api/docs/guides/decisions) 与 [Unite.AI 的逐项整理](https://www.unite.ai/openai-makes-decisions-api-generally-available-with-gpt-6-luna/) 交叉核对：确认端点、三种问题类型、Luna 为唯一支持模型、400 个问题上限、“快至多 10 倍”的表述，以及价格 0.10 美元/百万输入 token、缓存 0.01 美元、只收输入费。素材里“输出免费”的说法成立，但要注意官方措辞是“不收取输出 token 费用”，区域处理溢价与长上下文倍率仍然另计，缓存读写的费率与 Luna 标准提示缓存一致。文档同时写明文件、音频与 item 引用不支持，依赖前一个答案的决策必须拆成多次请求。
- 判断：值得记住的不是 10 倍，而是计费口径的改变：把成本压到只剩输入，等于鼓励“一次带很多问题”，这会直接改变 Agent 的调用结构——从“每步问一次模型”转向“一次问 400 个判定”。风险也在同一处：400 个问题共享同一段上下文，问题与问题之间的相关性越强，越容易一起错。

### Google 在 AGNTCon 发布 Agent Compute Engine，并把 Gemini 的企业 Agent 治理外扩

- 发生了什么：Google Cloud 10-22 在 AGNTCon + MCPCon 发布 Agent Compute Engine（ACE），一个为 Agent 生命周期专门设计的算力服务，目前在为 Gemini 的工作型 Agent 提供支撑，将在未来数月进入预览。每个 Agent 获得一台硬件隔离的 microVM：Cloud Hypervisor 边界、独立 guest kernel 与 root 权限、自己的 Hyperdisk 做会话持久化、短时效凭证与密码学可验证的 ID，凭证在 microVM 之外的出口注入；空闲 microVM 通过 checkpoint/restore 暂停以省资源，多 Agent 靠 copy-on-write 共享同一份系统模板。同期把 Gemini for business 的 Agent 治理能力扩展为 Agent Gateway、Agent Registry 等组件，并公开了跑在 GKE 上的开源运行时 Agent Substrate。
- 为什么值得关注：多 Agent 的成本结构里，真正贵的是“等待”：Agent 在等工具返回、等人类确认时占着机器不放。ACE 的这套设计与 Agent Substrate 的实测口径都指向同一件事：把空闲态成本压到接近零。Google 公布的数字是 Agent Substrate 在 20 万个 Agent 的压测中维持每秒 500 次激活、挂起与恢复延迟低于 500 毫秒，计算密度最高为传统方式的 10 倍。对买方而言，这意味着“每个 Agent 一台机器”这种听起来昂贵的模型第一次有了可行价格。
- 原帖与互动：[Google Cloud 官方帖](https://x.com/googlecloud/status/2113285915258794378)（10-22 23:06，2.1 万浏览、197 赞、27 转、18 回复）。同日的 Gemini API CLI 由两名 Google 员工先发：[EvanOtero](https://x.com/EvanOtero/status/2113342374713938089)（10-23 02:51，6144 浏览、99 赞、4 转、5 回复）与 [vamsibatchuk](https://x.com/vamsibatchuk/status/2113309268216778905)（10-23 00:39，3871 浏览、101 赞、4 转、10 回复），官方账号未单独发帖。
- 核验：[Google Cloud 官方博客](https://cloud.google.com/blog/topics/ai-infrastructure/introducing-agent-compute-engine-and-expanded-agent-governance)确认了 microVM 架构、Titanium IPU 的硅级隔离、Hyperdisk 持久化、Agent Gateway 与 Agent Registry 的治理范围，以及“未来数月进入预览”这一时间口径（有媒体写成“今年晚些时候”，与官方原文略有差别）。[GKE Agent Substrate 博客](https://cloud.google.com/blog/products/containers-kubernetes/agent-substrate-available-on-gke) 确认 10 倍密度、每秒 500 次激活、200,000 个 Agent 压测与开源可移植性。Gemini API CLI（gemini-api）经 [官方仓库](https://github.com/google-gemini/gemini-api-cli) 确认：Apache 2.0 的单一 Go 二进制，预览/实验状态，覆盖文本生成、图像（默认 gemini-nano-banana-2.1）、TTS、音乐（lyria-3.5）、视频（gemini-omni-1.1-flash）、文件分析与转录，并能把媒体文件直接写到磁盘、只回传路径，还带 --dry-run 与 --schema 供 Agent 自查，托管 Agent 可以后台运行并回传 interaction ID。
- 判断：ACE 与 CLI 是同一件事的两端：一端把 Agent 的运行环境标准化成“一人一台虚拟机”，一端把 Google 的模型能力包装成 Agent 可以直接调用的命令行。对第三方 Agent 框架来说，后者比前者更现实——不需要迁云，只要在 shell 里多一个可执行文件。需要保留的疑问是预览时间：官方口径是“未来数月”，而 Agent 治理与企业身份的完整链路通常比算力上线慢得多。

### Hugging Face 开源 Carbon-X：能读 DNA 的 14B 模型，距前沿只差 0.8 分但便宜约 1800 倍

- 发生了什么：Hugging Face 10-22 发布 Carbon-X，从 Qwen3-14B 出发、14.8B 参数的 DNA 与自然语言联合模型，Apache 2.0。做法是单一解码器、单一 token 流：文本继续用 Qwen3 的 BPE 词表，DNA 用不重叠的 6-mer 编码成一个 token，共 5,515 个 DNA token，不另设 DNA 编码器；中训练用了 302B token 的 DNA、生物文本、英文与指令数据，再经 SFT 与可验证奖励的强化学习。五项 DNA 基准平均 66.7%，官方称比基座 Qwen3-14B 高 27 分，略低于 GPT-6.1 Sol 的 67.5%，但每题推理成本约为后者的 1/1800；bf16 权重可放进一张 80GB 卡。同期 Clement Delangue 与 Thom Wolf 公开批评前沿实验室的生物安全过滤把科学家挡在外面。
- 为什么值得关注：把 DNA 做成“6 个碱基一个 token”的普通词表扩展，让模型可以直接在对话里读序列并解释判断依据，这比另建专用模型更接近研究者的使用方式：粘贴序列、问问题、拿到带推理的回答。成本那一段才是重点：官方估算用 Carbon-X 分析 ClinVar 里 240 万个意义未明变异约需 300 美元，而用他们评测的前沿模型需 3.2 万到 400 万美元。
- 原帖与互动：[作者 @_lewtun](https://x.com/_lewtun/status/2113214040516268126)（10-22 18:21，1.9 万浏览、203 赞、32 转、27 回复）给出“接近 GPT-6.1 Sol、成本低 1000 倍以上”的说法；[Clement Delangue](https://x.com/ClementDelangue/status/2113264393756545449)（10-22 21:41，5.6 万浏览、905 赞、115 转、55 回复）批评“前沿实验室在生物能力上往前跑，却用宽而浅的护栏拦住科学家，而坏人轻松绕过”，并称自己被某链接拦了；[Thom Wolf](https://x.com/Thom_Wolf/status/2113345703485309335)（10-23 03:04，7484 浏览、102 赞、12 转、18 回复）讲了个具体的笑话：写这条帖时，助手被生物安全过滤切断，而它正在总结的是自家今天发布的模型笔记。
- 核验：[模型卡](https://huggingface.co/HuggingFaceBio/Carbon-X)确认了 14.8B 参数、Qwen3-14B 基座、6-mer 分词、302B 中训练 token、40,960 token 上下文、Apache 2.0，以及 66.7% 对 67.5% 的对比与“约 1/1800 每题成本”的原始表述——注意官方写的是 1/1800，素材里的“低 1000 倍以上”是保守转述，两者方向一致但精度不同；同页也写明 Carbon-X 未经临床验证、不得用于医疗决策，并列出长输入未充分评测、thinking 模式未训练等限制。[Hugging Face 的发布页](https://huggingface.co/spaces/HuggingFaceBio/Carbon-X-Release) 与 [Business Insider 报道](https://www.businessinsider.com/hugging-face-ai-model-carbon-x-dna-sequences-gene-therapies-2026-10) 补充了合作方（中关村学院、TIGEM/那不勒斯费德里科二世大学）与“可对话式读 DNA”的定位。[The Next Web](https://thenextweb.com/news/hugging-face-carbon-x-dna-ai-model) 也提到该模型尚无湿实验验证。
- 判断：0.8 分的差距不值得当成“追平前沿”，值得记的是成本曲线：当每题成本差三个数量级时，很多以前因为预算做不了的大规模变异筛查会变成现实。Delangue 与 Wolf 的批评属于立场表达，不是可核事实，但它指向一个具体产品问题：生物安全过滤目前既不透明也不一致，同一个助手会拦住自家模型的发布笔记，这种误伤正是用户流失的原因。

### LiteLLM 1.107.0 再遭供应链攻击：官方 PyPI 包与 Docker 镜像被植入后门

- 发生了什么：10-21 发布的 LiteLLM 1.107.0 被发现是恶意版本，PyPI 上全部七个 wheel 与官方 Docker 镜像（含 latest、main-stable 浮动标签）受影响。恶意代码通过 .pth 机制与 sitecustomize.py 在 Python 启动时自动执行，窃取云凭证、AI 供应商 API key、SSH 私钥，并从攻击者控制的 GitHub 仓库取回域名后拉取远端代码编译执行，可实现远程代码执行；还带 fork/setsid 守护化、用 /tmp 锁文件与约每小时轮询维持驻留。LiteLLM 官方称攻击者通过三名工程师的 GitHub 账号操作，判断是 GitHub CLI 的 OAuth token 被盗，攻击者曾试图改动发布流水线让发布指向另一个源码仓库。安全版本回退到 1.106.2，官方源码 tag 本身干净——问题出在构建环境。同周 Railway、Zeabur、OpenCode 也各出安全事件。
- 为什么值得关注：LiteLLM 是大量团队接多家模型供应商的统一入口，它所在的环境天然握着所有供应商的密钥，所以一次失守等于全线凭证暴露。这次的技术细节比“又一个投毒包”更值得抄进检查清单：恶意文件不在 git tag 里，只存在于构建产物，因此只审源码、只对 tag 做 diff 的流程完全看不到它；而启动钩子意味着“在受影响环境里跑 pip 卸载”本身就会重新触发。
- 原帖与互动：[The Hacker News](https://x.com/TheHackersNews/status/2112967698103894257)（10-22 02:02，6.4 万浏览、387 赞、96 转、38 回复）是最早扩散的一批；[SlowMist](https://x.com/SlowMist_Team/status/2113113355917619560)（10-22 11:40，3447 浏览、28 赞、9 转、15 回复）给了处置建议与“钉在 1.106.2”的具体版本号；[DailyDarkWeb](https://x.com/DailyDarkWeb/status/2112971516690432179)（10-22 02:17，5944 浏览、12 赞、1 转、3 回复）补充了“92M+ 月下载量”与“不要用 pip 自救”的提醒；[一条把十月串起来的清单帖 @infinterenders](https://x.com/infinterenders/status/2113148214115492337)（10-22 13:59，4625 浏览、123 赞、11 转、10 回复）把 LiteLLM 与 Railway、Zeabur、OpenCode 等并列。
- 核验：[LiteLLM 官方事件报告](https://docs.litellm.ai/blog/security-incident-oct-21-2026)确认了“三名工程师的 GitHub 账号、疑似 GitHub CLI OAuth token 被盗”、攻击者试图让发布器指向别的源码仓库、以及源码 tag 不含恶意文件的结论；[Upwind 的分析](https://www.upwind.io/feed/litellm-1-107-0-supply-chain-attack-malicious-code-found-in-pypi-package)（漏洞的发现方，已在 [GitHub issue #47826](https://github.com/BerriAI/litellm/issues/47826) 中署名）确认了七个 wheel 全受影响、cook.pth / cook.py / sitecustomize.py 三件套、投递域名是仿冒的 litellm.dev（与官方 litellm.ai 无关）、以及每小时拉取新载荷的驻留行为；[Wiz 的分析](https://www.wiz.io/blog/litellm-compromised-steals-credentials)与 [Help Net Security 报道](https://www.helpnetsecurity.com/2026/10/22/litellm-compromised-supply-chain-attack-pypi-docker/) 交叉一致。需要说明的是，截至核验时该事件主要通过官方博客与第三方安全厂商披露，GitHub 安全公告库尚未出现对应条目。
- 判断：对使用方只有三条动作有意义：确认没有装过 1.107.0、从干净镜像重建而不是就地卸载、把所有该环境能碰到的凭证轮换一遍。更长远的一条是流程层面的：软件物料清单只覆盖源码不够，构建产物与发布流水线的权限才是这轮攻击真正的入口，三名工程师的 OAuth token 就能改发布目标，说明发布权限本身就是最高危的攻击面。

### MIT 的 OPAL 让 Agent 在训练中重写优化器代码

- 发生了什么：MIT 研究者 Xingjian Bai、Jia-Hao Liang、Jayden Teoh、Vincent Sitzmann 10-21 发布 OPAL（OPtimizer with an Agent in the Loop）：把 LLM agent 放进训练循环，观察损失与梯度动态、读文档、然后重写优化器本身的源码，而不是在外层调超参。实验覆盖图像生成与语言建模四类任务，官方称在 LightningDiT-XL/1（FID-50K 1.83 对官方配方 2.18，带 guidance）、RAEv2-B（3.19 对 3.39）与 modded-nanogpt Track 3 上优于或追平人工配方；每次运行约 100 次决策，用 Claude Opus 5.5 的 token 成本约 6.42 美元，对比约 74 个 H100 小时的训练开销。
- 为什么值得关注：这是把“优化器设计”从人写公式变成 agent 写代码，且明确是零样本、不跨运行学习。它给出的成本对照很有说服力：token 钱相对于 GPU 小时几乎可以忽略，意味着“让模型改训练代码”在经济上已经不成问题，问题转移到可靠性与可审计性。
- 原帖与互动：[Robert Lange 的解读](https://x.com/RobertTLange/status/2113352327042117692)（10-23 03:30，1196 浏览、37 赞、2 转、4 回复）强调“它不是外层超参调优器”；[Google 的 Laurence Moroney](https://x.com/lmoroney/status/2113143520831918485)（10-22 13:40，734 浏览、4 赞、0 转、4 回复）用一句话概括“优化器会在训练中改写自己”；[一条更尖锐的评论 @toankhontech](https://x.com/toankhontech/status/2113114737248809111)（10-22 11:46，167 浏览、4 赞、0 转、3 回复）指出仓库自己承认多数实验只跑一次、且 agent 无法回滚错误决定。三条帖子互动都低，属于研究圈内传播。
- 核验：[作者博客《Reactive Optimizers》](https://xingjianbai.com/reactive-optimizers/)是主要一手来源，确认作者名单、Claude Opus 5.5 驱动 agent、四组任务的具体数字与成本核算，并明确写该方法“完全零样本、不从重复运行中学习任何东西”，同时承认按 FLOPs 计这种做法在前沿规模上不现实——它的定位是“对大多数研究者而言，GPU 小时比 token 更贵”。[GitHub 仓库](https://github.com/xingjian-bai/opal)与 [PyPI 说明](https://pypi.org/project/opal-optimizer/) 补充了工程约束：需要在本机装好并登录 Claude Code（费用记在用户账号上、默认无上限）、支持 CPU 单卡与单节点 DDP、agent 只能在下一次决策点改程序而不能重启或回滚训练，文档也提醒“错误决定会让一次运行变差”。素材里把它称为 arXiv 论文不准确，目前公开的是一篇带完整脚注的博客与可安装代码，未检索到 arXiv 编号。
- 判断：这条的正确读法是“成本论证成立、可靠性论证未成立”。一次运行只有约 100 次决策、多数实验只跑一次、失败不能回滚，这三点放在一起意味着结论的方差没有被量化。真正会决定它能否进入生产训练的，不是那几组 FID，而是有没有人做出“agent 改坏了怎么办”的护栏。
